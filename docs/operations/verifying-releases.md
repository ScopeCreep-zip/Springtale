# Verifying Springtale releases

Springtale releases are signed with [Sigstore cosign][cosign] in keyless
OIDC mode, with SLSA Build Level 3 provenance attestation generated by
the [SLSA GitHub generator][slsa-gen]. Both artefacts are published to
the [Sigstore Rekor transparency log][rekor] so any user can verify the
release was built on Springtale's GitHub Actions and not a substituted
binary from somewhere else.

This page is the verification recipe. Run it on every release before
trusting the binary.

[cosign]: https://docs.sigstore.dev/cosign/overview/
[slsa-gen]: https://github.com/slsa-framework/slsa-github-generator
[rekor]: https://docs.sigstore.dev/logging/overview/

## Prerequisites

```
# macOS
brew install cosign

# Linux (binary release)
curl -sSfL https://github.com/sigstore/cosign/releases/latest/download/cosign-linux-amd64 \
  -o cosign && chmod +x cosign && sudo mv cosign /usr/local/bin/

# Nix
nix-shell -p cosign
```

Verify cosign itself:

```
cosign version
```

## Verify a binary

Download the artifact and its `.cosign.bundle` from the GitHub Release.
Then:

```
cosign verify-blob \
  --bundle springtaled.cosign.bundle \
  --certificate-identity-regexp '^https://github\.com/ScopeCreep-zip/Springtale/\.github/workflows/.+@refs/tags/v.+' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  springtaled
```

A successful run prints `Verified OK` and exits 0. Any mismatch — wrong
identity, wrong issuer, tampered binary — exits non-zero. Do not run the
binary if verification fails.

## Verify SLSA provenance

```
cosign verify-attestation \
  --type slsaprovenance \
  --certificate-identity-regexp '^https://github\.com/slsa-framework/slsa-github-generator/' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  springtaled
```

The provenance attestation includes:

- The exact GitHub Actions workflow path + commit SHA that built the artifact
- Build invocation parameters (cargo flags, environment variables in scope)
- The dep graph (via `cargo-auditable` embedding) so a downstream
  `osv-scanner sbom-from-binary` can re-derive what was linked in

## Verify SBOM

The release ships both CycloneDX 1.7 (primary) and SPDX 2.3 (secondary)
SBOMs, each signed independently:

```
cosign verify-blob \
  --bundle springtale.cdx.json.cosign.bundle \
  --certificate-identity-regexp '^https://github\.com/ScopeCreep-zip/Springtale/' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  springtale.cdx.json
```

Inspect the SBOM:

```
# Component count
jq '.components | length' springtale.cdx.json

# All Rust deps + versions
jq -r '.components[] | select(.purl | startswith("pkg:cargo/")) | "\(.name) \(.version)"' springtale.cdx.json
```

## Verify against the Rekor transparency log

cosign-verify above implicitly checks Rekor. To inspect the entry
directly:

```
COSIGN_EXPERIMENTAL=1 cosign tree springtaled
```

Or by-hand:

```
rekor-cli search --artifact springtaled
rekor-cli get --uuid <uuid>
```

## What to do if verification fails

1. **Stop**. Don't run the binary.
2. Check the GitHub Release page — has it been updated since you downloaded?
3. Re-download from the official release page.
4. Re-verify.
5. If it still fails, the most likely scenarios are:
   - You're verifying against the wrong repo identity. Double-check the regex.
   - The release page was tampered with on a mirror.
   - Real incident — file a vulnerability report per
     [`SECURITY.md`](../../SECURITY.md).

## Why we use keyless

Keyless signing binds each signature to a one-time Sigstore certificate
issued at build time, tied to the GitHub OIDC identity of the workflow
that built the artefact. Compared to a long-lived signing key:

- No private key to lose or have stolen
- No key rotation flow
- The "identity" being verified is the source repository + workflow path,
  which is what users actually care about (provenance), not who held the
  key at signing time

For Springtale specifically this matters because the project supports
anonymous and pseudonymous maintainership. Sigstore lets us prove
"this release came from the canonical Springtale repo on GitHub Actions"
without ever having to publish a personal key.

## Reproducing the build

For users who want to go further than verifying — reproduce the build
locally and compare hashes:

```
git clone --branch v0.2.0 https://github.com/ScopeCreep-zip/Springtale
cd Springtale
SOURCE_DATE_EPOCH=$(git log -1 --format=%ct) \
  cargo auditable build --release --locked --bin springtaled --bin springtale-cli
sha256sum target/release/springtaled
```

Compare against the SHA-256 from the release notes / SLSA provenance.
Differences may be due to upstream rustc non-determinism; track the
posture in `docs/security/SUPPLY-CHAIN.md`.
